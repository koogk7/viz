빅테크 서브레저·회계 시스템 아키텍처 리서치

2026-06-07 Claude 세션 리서치 정리. 빅테크/핀테크의 회계처리 서버 아키텍처 → sub-ledger 데이터 수신·모델링 심화 순으로 조사.

1. 공통 구조: Sub-ledger / GL 2계층

비즈니스 이벤트 → [Sub-ledger 계층: 엔지니어링 소유]
  Kafka 등 이벤트 수집 → 복식부기 ledger (immutable, append-only)
  → Reconciliation (PSP/은행 3-way 대사)
  → 집계/Rollup (계정과목×법인×통화×일자)
  → [GL 계층: 재무 소유] 상용 ERP (SAP/Oracle/NetSuite) → 월마감/감사/공시
  • 거래량 때문에 GL에 건별 적재 불가 → "실시간·고볼륨 = sub-ledger, 저볼륨·고통제 = ERP"
  • 팀 구조: 파이프라인 배관 = Finance Engineering, 매핑 룰 내용 = Controllership(회계), ERP = Finance Systems
  • 정정은 UPDATE가 아닌 reversal entry. 차대변 합=0을 시스템이 강제

2. 데이터 수신·모델링 패턴 (회사별 비교)

회사 모델링 전략 핵심 아이디어
Airbnb 이벤트 2단 변환 platform/payment event → event handler → accounting event. (product type+ID)=최소 회계 단위. 모든 제품을 공통 생애주기(계약→자금이동→이행→정산)에 매핑. 정정은 delta 대신 un-book→re-book
Stripe 계정=type+properties, 이벤트=상태전이 producer 시스템을 상태머신으로 인코딩. 계정=상태, 이벤트=잔액 이동. 이벤트끼리 독립·순서 비보장 전제, 식별자로 fund flow 연결. Clearing/Timeliness/Completeness 검증 내장
Square (Books) 3-테이블 범용 스키마 books / journal_entries / book_entries. 이종 제품은 shelf(tenant)+user_data로 격리, 코어 스키마는 순수 복식부기만. Spanner 인터리빙, monotonic version counter
Uber (LedgerStore) document 모델 + 저장소 레벨 보증 datastore▸table▸records-as-documents로 이종성 흡수. 불변 레코드(1.2PB)/가변 인덱스(0.5PB) 분리. 인덱스는 2PC 강일관성. sealing=30분 윈도우+서명된 manifest(체크섬+키서명)로 재현성·변조탐지 보장
Adyen 검증된 템플릿 분개는 템플릿으로만 생성, 템플릿 변경마다 모든 입력 조합 합=0을 수학적으로 자동 증명
Nubank 불변 DB 활용 Datomic(append-only DB) 위에 실시간 복식부기 → ledger immutability가 DB 속성으로 공짜
Robinhood 청산 원장을 스트림으로 자체 청산(2018~). Kafka exactly-once 스트림 복식부기, Airflow 일마감 300+ jobs. 2020년 위기 때 "ledger entry↔잔액의 원자성 포기, eventual consistency 허용"으로 10x 처리량

3. 가로지르는 설계 원칙

  1. 비즈니스 이벤트와 회계 이벤트를 분리 — 중간 변환 계층이 이종 데이터 흡수의 핵심
  2. 코어 스키마는 좁게, 제품 의미는 properties/metadata로 — 복식부기 불변식만 코어에서 강제
  3. 순서 비보장·독립 도착 전제 — 식별자 연결, 트랜잭션으로 묶지 않음
  4. 정정 = reversal/re-book (immutability와 세트)
  5. Completeness 검증이 1급 시민 — source DB ID 전수 대조 (Uber는 Spark로 7,600억 건 offline validation)
